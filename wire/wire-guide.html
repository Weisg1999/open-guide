1. 项目简介入门

Wire 是 Google Go Cloud 团队 2018 年从 go-cloud 拆出的编译期依赖注入工具，v0.3 起宣称功能完备，2025 年 8 月仓库被自动归档，README 明确写着 This project is no longer maintained。它只做一件事：你写注入函数的签名，它生成函数体。

  • Provider：普通构造函数 func NewXxx(a A, b B) (*Xxx, func(), error)。参数是依赖，第一个返回值是产物，第二个可选返回值是清理函数，最后一个是 error。它不 import wire，单独调用也能工作。
  • Injector：签名由你写、函数体只有一行 wire.Build(...) 的函数。wire 从它的返回值反推整条依赖链，按拓扑序生成普通 Go 代码。
wire.go（//go:build wireinject）      ── wire gen ──▶   wire_gen.go（//go:build !wireinject）
手写 injector 签名 + wire.Build(Set)                  普通构造函数调用序列，入库、可 review、可断点

为什么用编译期 DI：生成的 wire_gen.go 就是你会手写的那种代码——初始化顺序、错误分支、清理时机全部显式；运行期没有反射、没有容器、没有启动扫描；装配错误（缺 provider、循环依赖、类型歧义）在 go build 之前暴露，而不是等某个 handler 第一次取依赖时 panic；IDE 能跳转、能下断点、能直接单测 provider。代价是多一个生成步骤、「类型即契约」（同类型不能有两个实例）、生成文件必须入库，且上游已归档不再有新特性。

安装只要一行：go install github.com/google/wire/cmd/wire@v0.7.0（只装 CLI，业务代码不 import；也可在模块内 go run github.com/google/wire/cmd/wire@v0.7.0 ./... 锁版本）。生成文件头部自带 //go:generate go run -mod=mod github.com/google/wire/cmd/wire，所以 go generate ./... 也能触发，不必人人装 CLI。

3. 核心概念与原理核心

3.1 求解过程：从返回值反推整张图

wire 先加载带 wireinject tag 的包，找出函数体只有 wire.Build 的函数，再从返回值出发反向求解：

需要 *HTTPServer      → NewHTTPServer(cfg, UserStore, *slog.Logger)
需要 UserStore        → 只有 wire.Bind 声明，转去要 *store.UserRepo
需要 *store.UserRepo  → NewUserRepo(*sql.DB, *redis.Client)
需要 *sql.DB          → db.Open(cfg, *slog.Logger)   ← 自带 cleanup 与 error
需要 config.Config    → config.Load()                ← 叶子，无依赖
  • 类型匹配用 type identity：string 与 type UserID string 是两个类型，Foo 与 *Foo 也是（wire.Struct 是少数同时提供两者的例外）。
  • 同一类型只能有一个 provider，且检查整个传递闭包，不只是 wire.Build 的直接参数；同一个 provider 在 set 里出现两次也报错，wire 不去重。
  • 只生成用得到的路径，没被依赖的 provider 不会进入 wire_gen.go；wire.go 里的非 injector 声明（如 ProviderSet）会被原样复制到生成文件。
  • injector 可以带参数（func InitApp(cfg config.Config) (...)），这些参数成为图的输入，由调用方构造。

3.2 双 build tag 与 wire_gen.go 的生成契约

stub 与生成物用互斥的 build tag 保证同名函数在任一编译单元里只有一份定义：

//go:build wireinject
// +build wireinject

package server

func InitApp() (*HTTPServer, func(), error) {
	panic(wire.Build(ProviderSet)) // 函数体只给 wire 看
}

生成的 wire_gen.go 顶部是 //go:build !wireinject + // +build !wireinject：wire 工具需要「含 stub、不含实现」的视图做分析，go build 需要「含实现、不含 stub」的视图，否则同名函数 redeclared in this block。// +build 是 Go 1.17 之前的老式约束，与 //go:build 之间要空一行，gofmt 会保留两行。

  • wire_gen.go 必须提交：CI 只跑 go build/go test 时不会装 wire，缺它就是 undefined: InitApp；提交还能让 review 看到装配顺序变化。
  • 防漂移：CI 重新生成后 git diff --exit-code，或直接 wire diff ./...（有差异退出码 1，出错 2）。
  • 手改一定被覆盖：wire gen 是整文件重写，不是 patch；首行固定 // Code generated by Wire. DO NOT EDIT.。

3.3 ProviderSet 分层与标记函数

按「层」组织 set，依赖方向单向 server → store → db/cache，set 跟着单向嵌套：

var ConfigSet = wire.NewSet(Load)
var InfraSet = wire.NewSet(ConfigSet, logx.New, db.Open, cache.NewRedis)
var ProviderSet = wire.NewSet(InfraSet, store.NewUserRepo,
	wire.Bind(new(UserStore), new(*store.UserRepo)), NewHTTPServer)

wire.Bind 是「接口 → 具体类型」的桥：Go 惯例是 provider 返回具体类型，消费方依赖接口。第二个参数是「指向具体类型的指针的指针」——provider 返回 *UserRepo 就写 new(*UserRepo)；被绑定的具体类型必须在同一个 set 里有 provider，否则报 provider set does not include a provider for *store.UserRepo。

wire.Struct 在字段本身就是依赖时省掉构造函数：

type HTTPServer struct {
	srv   *http.Server
	store UserStore
	log   *slog.Logger
	mu    sync.Mutex `wire:"-"` // 排除，wire 不会去图里找 sync.Mutex
}

var ServerSet = wire.NewSet(wire.Struct(new(HTTPServer), "*")) // 同时提供 HTTPServer 与 *HTTPServer

字段必须导出（unexported 自动跳过）；"*" 表示全填；显式点名被 wire:"-" 排除的字段会直接报错；旧写法「把 struct 值直接放进 NewSet」已废弃。wire.Value / wire.InterfaceValue 则给常量一个 provider，避免写只返回常量的函数——表达式会被复制到生成文件并在包初始化时求值，因此不能含函数调用或 channel 接收，且 Value 不接受接口类型（接口用 InterfaceValue）；wire.FieldsOf 把已构造结构体的字段提升为 provider，省掉 getXxx。

3.4 cleanup：顺序、错误与「只能是 func()」

清理函数签名必须是 func()——wire 的类型检查只认 func()，写成 func() error 会报 second return type is func() error; must be error or func()。清理中的错误只能在闭包里自己记日志，wire 不聚合清理错误。顺序由生成器保证：清理与构造顺序相反。

sqlDB, cleanup, err := db.Open(configConfig, logger)
if err != nil {
	return nil, nil, err
}
client, cleanup2, err := cache.NewRedis(configConfig)
if err != nil {
	cleanup() // 中途失败：已建资源立即回收
	return nil, nil, err
}
return httpServer, func() {
	cleanup2() // 后构造的先清理
	cleanup()  // 先构造的后清理
}, nil

只要 provider 集合里任意一个 provider 带 cleanup（或 error），injector 签名就必须预留对应位置，顺序固定为「产物、func()、error」。

3.5 类型唯一性：同类型多实例怎么破

wire 不允许同一类型有两个 provider，因为大多数情况下那是 bug。真实项目确实有「主库 + 从库」「缓存 Redis + 锁 Redis」，官方解法不是命名参数，而是造一个新类型：type ReplicaDB struct{ *sql.DB } 包一层，再给 OpenReplica(cfg) (*ReplicaDB, func(), error)，需要从库的仓储就声明 NewReportRepo(primary *sql.DB, replica *ReplicaDB)。指针别名（type ReplicaDB = sql.DB）无效，别名与原类型 type identity 相同。也可以 type DSN string 区分基础类型配置，或拆 injector 把互斥 provider 分到不同图。Bind 不是解法——它只是给同一实例加接口视图。

3.6 生成期会拒绝的五类错误

no provider found for X（补 provider 或 injector 参数）、cycle for X（拆接口或注入工厂函数）、multiple providers for X（命名类型包装）、Bind 缺具体实现（把 NewImpl 加进同一 set）、injector 签名不匹配（补齐 func() / error 返回位）。这些检查都在生成阶段完成，wire diff 也跑同一套分析，放进 CI 相当于给装配图加了一道编译期单测。

4. 使用实战实战

目标：HTTP 服务 + MySQL + Redis + slog，走通 config → infra → repo → transport 四层，演示 wire.Bind 与 cleanup。

4.1 目录与 provider

demo/
├── cmd/server/main.go            # 只管进程：启动、信号、优雅退出
└── internal/
    ├── config/config.go          # Load() → Config
    ├── logx/logx.go              # New() → *slog.Logger
    ├── db/db.go                  # *sql.DB + cleanup + error
    ├── cache/redis.go            # *redis.Client + cleanup + error
    ├── store/user.go             # *store.UserRepo
    └── server/{http.go,wire.go,wire_gen.go}

两个叶子 provider 从略：config.Load() 从 ADDR / MYSQL_DSN / REDIS_ADDR 读环境变量并给默认值，返回 Config{Addr, DSN, RedisAddr}；logx.New() 返回一个 JSON handler 的 *slog.Logger。它们没有任何依赖，是最简单的 provider 形态。

// internal/db/db.go
package db

import (
	"database/sql"
	"log/slog"

	_ "github.com/go-sql-driver/mysql"

	"example.com/demo/internal/config"
)

func Open(cfg config.Config, log *slog.Logger) (*sql.DB, func(), error) {
	conn, err := sql.Open("mysql", cfg.DSN)
	if err != nil {
		return nil, nil, err
	}
	return conn, func() {
		if err := conn.Close(); err != nil {
			log.Error("close mysql", "err", err) // cleanup 只能是 func()，错误在这里收口
		}
	}, nil
}

cache.NewRedis(cfg config.Config) (*redis.Client, func(), error) 与 db.Open 同构——建客户端、返回 Close 闭包，这里不再重复贴代码。

// internal/store/user.go —— 只依赖具体资源，不认识任何接口
package store

import (
	"context"
	"database/sql"

	"github.com/redis/go-redis/v9"
)

type UserRepo struct {
	db  *sql.DB
	rdb *redis.Client
}

func NewUserRepo(db *sql.DB, rdb *redis.Client) *UserRepo { return &UserRepo{db: db, rdb: rdb} }

func (r *UserRepo) Get(ctx context.Context, id int64) (string, error) {
	var name string
	err := r.db.QueryRowContext(ctx, "SELECT name FROM users WHERE id = ?", id).Scan(&name)
	return name, err
}
// internal/server/http.go —— 接口定义在消费方，store 不需要 import 本包
package server

import (
	"context"
	"log/slog"
	"net/http"
	"strconv"
	"strings"
	"time"

	"example.com/demo/internal/config"
)

type UserStore interface {
	Get(ctx context.Context, id int64) (string, error)
}

type HTTPServer struct {
	srv   *http.Server
	store UserStore
	log   *slog.Logger
}

func NewHTTPServer(cfg config.Config, store UserStore, log *slog.Logger) *HTTPServer {
	h := &HTTPServer{store: store, log: log}
	mux := http.NewServeMux()
	mux.HandleFunc("/users/", func(w http.ResponseWriter, r *http.Request) {
		id, err := strconv.ParseInt(strings.TrimPrefix(r.URL.Path, "/users/"), 10, 64)
		if err != nil {
			http.Error(w, "bad id", http.StatusBadRequest)
			return
		}
		name, err := h.store.Get(r.Context(), id)
		if err != nil {
			h.log.Error("get user", "id", id, "err", err)
			http.Error(w, "internal error", http.StatusInternalServerError)
			return
		}
		_, _ = w.Write([]byte(name))
	})
	h.srv = &http.Server{Addr: cfg.Addr, Handler: mux, ReadHeaderTimeout: 5 * time.Second}
	return h
}

func (h *HTTPServer) Start() error                       { return h.srv.ListenAndServe() }
func (h *HTTPServer) Shutdown(ctx context.Context) error { return h.srv.Shutdown(ctx) }

4.2 wire.go：手写的只有签名与集合

//go:build wireinject
// +build wireinject

package server

import (
	"github.com/google/wire"

	"example.com/demo/internal/cache"
	"example.com/demo/internal/config"
	"example.com/demo/internal/db"
	"example.com/demo/internal/logx"
	"example.com/demo/internal/store"
)

// ProviderSet 按层组合：配置 → 基础设施 → 仓储 → 传输层。
var ProviderSet = wire.NewSet(
	config.Load,
	logx.New,
	db.Open,
	cache.NewRedis,
	store.NewUserRepo,
	wire.Bind(new(UserStore), new(*store.UserRepo)),
	NewHTTPServer,
)

func InitApp() (*HTTPServer, func(), error) {
	panic(wire.Build(ProviderSet))
}

4.3 生成后的 wire_gen.go

// Code generated by Wire. DO NOT EDIT.

//go:generate go run -mod=mod github.com/google/wire/cmd/wire
//go:build !wireinject
// +build !wireinject

package server

import (
	"example.com/demo/internal/cache"
	"example.com/demo/internal/config"
	"example.com/demo/internal/db"
	"example.com/demo/internal/logx"
	"example.com/demo/internal/store"
)

func InitApp() (*HTTPServer, func(), error) {
	configConfig := config.Load()
	logger := logx.New()
	sqlDB, cleanup, err := db.Open(configConfig, logger)
	if err != nil {
		return nil, nil, err
	}
	client, cleanup2, err := cache.NewRedis(configConfig)
	if err != nil {
		cleanup()
		return nil, nil, err
	}
	userRepo := store.NewUserRepo(sqlDB, client)
	httpServer := NewHTTPServer(configConfig, userRepo, logger)
	return httpServer, func() {
		cleanup2()
		cleanup()
	}, nil
}

对照四点：Bind 不产生额外代码，*store.UserRepo 被直接传给要 UserStore 的 NewHTTPServer（Go 隐式接口赋值）；cleanup 按 cleanup、cleanup2 递增命名，最终闭包逆序调用；无依赖的 Load/New 排在最前；wire.go 里的 ProviderSet 会被原样复制到文件末尾（上面略去该段，真实生成文件因此还会 import wire——那只是 marker 类型，无 init 逻辑）。

4.4 main.go：进程生命周期与清理时序

func main() {
	app, cleanup, err := server.InitApp()
	if err != nil {
		log.Fatalf("init app: %v", err) // 失败时 cleanup 为 nil，不要 defer
	}
	defer cleanup() // 逆序：先关 redis，再关 mysql

	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
	defer stop()
	go func() { _ = app.Start() }()
	<-ctx.Done()

	// 顺序不能反：先停流量、等在途请求结束，最后由 cleanup 关连接池。
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := app.Shutdown(shutdownCtx); err != nil {
		log.Printf("shutdown: %v", err)
	}
}

（main 的 import：context、log、os/signal、syscall、time 与 example.com/demo/internal/server。）

4.5 生成与 CI 校验

wire ./...                  # 全仓生成，等价于 wire gen ./...
wire show ./internal/server # 列出 ProviderSet 的导入关系、可产出类型与 injector
wire diff ./... || { echo "wire_gen.go 与 wire.Build 不一致"; exit 1; }  # 有差异退出码 1

provider 带 build tag 时（如仅 Linux 编译的 provider），用 wire gen -tags=linux ./...，让分析器与 go build 用同一组 tag。

实战要点：wire_gen.go 要入库，并在 CI 里重新生成比对，防止有人手改生成文件。

5. 版本演进版本

Wire 的版本史几乎就是「停更史」。截至 2026-11，仓库已归档，最后提交停在 2025-08-21，最后一个 tag 是 2025-08-22 的 v0.7.0。

版本时间要点
v0.3.02019.06宣布 beta 并承诺 API 稳定；新增 wire.Struct / FieldsOf；Bind 第二参数改为指针
v0.5.02021.01支持 --tags 指定分析用 build tag；go:generate 改用 go run
v0.6.02024.02.07仅升级 golang.org/x/tools 以支持 Go 1.22，无语义变化；go.mod 为 go 1.19
v0.7.02025.08.22升级 x/tools 修复 Go 1.25 构建失败 + README 加「不再维护」声明；仓库随后归档

API 面自 v0.3 起没再变过，「v0.6.x」与「v0.7.0」在写法上完全等价，差别只是能否在新工具链下构建。升级 wire 不会带来新能力，只可能是兼容性修复；要用新 go/types 特性的团队只能自己 fork——上游 README 正是这么建议的。

6. 常见坑与最佳实践避坑

  1. 忘了 //go:build wireinject：stub 参与正常构建，生成后立刻 InitApp redeclared in this block；生成前 panic(wire.Build(...)) 还会被打进二进制。→ 双 tag 都写，用空行与 package 隔开。
  2. 手改 wire_gen.go：下次 wire gen 整文件重写，改动无声消失。→ 要调顺序就改 wire.Build 的 set 或 provider 依赖；生成文件只读。
  3. 把 wire_gen.go 加进 .gitignore：CI 只跑 go build 就是 undefined: InitApp，本地能过只因你生成过。→ 生成文件必须入库并参与 review。
  4. ProviderSet 循环依赖：server 的 set 引 store，store 为拿 Config 反向引 server，编译期 import cycle。→ set 只沿依赖方向嵌套，公共类型下沉独立包。
  5. 同类型两个 provider：两个 *slog.Logger、两个 *redis.Client、两个 string 都报 multiple providers。→ 命名类型包装（3.5），别指望按字段名或参数名区分。
  6. 接口多实现混进同一张图：mock 与真实实现同时进 set，或 Bind 的目标类型没有 provider。→ 每个接口在单张图里只绑一个实现，mock 走独立 injector。
  7. 有 cleanup 却没调用：InitApp 的 cleanup 被 _ 丢掉，连接池不关、临时文件不删。→ defer cleanup() 紧跟成功判断；err != nil 时 cleanup 为 nil，别提前 defer。
  8. cleanup 写成 func() error：wire 只接受 func()，报 second return type is func() error; must be error or func()。→ 错误在闭包里 log.Error 收口。
  9. injector 漏返回值位：provider 带 cleanup/error，injector 只返回 *HTTPServer。→ 签名固定 (T, func(), error)，多余与否让 wire 告诉你。
  10. wire.Value 里放函数调用：wire.Value(time.Now()) 会在生成文件的包初始化阶段求值，且 wire 直接拒绝复杂表达式。→ 只放常量/字面量，要计算就写 provider。
  11. provider 返回接口：func NewStore() UserStore 让具体类型从图上消失，Bind 也失去意义。→ provider 一律返回具体类型，接口在消费方定义并用 Bind 连接。
  12. wire.Struct(new(S), "*") 撞上不该注入的字段：sync.Mutex、chan struct{}、测试专用字段都会触发 no provider found。→ 加 wire:"-"，或显式列字段名而不用 *。
  13. 优雅退出顺序写反：先 cleanup() 再 Shutdown，在途请求拿到已关的连接池，报 sql: database is closed。→ 先停监听、等在途请求，最后 cleanup。
  14. 把 wire 当活项目：仓库已归档，issue/PR 不再处理，新 Go 版本兼容只能等社区 fork。→ 锁 v0.7.0，把它当「稳定的生成器」而非演进中的框架；单个 injector 过大时按进程拆 InitAPI、InitWorker，共享下层 set。

生产警示：忘加 wireinject tag、手改生成文件被覆盖、接口多实现导致绑定歧义。

7. 选型对比决策

维度wireuber-go/fxuber-go/dig手动装配samber/do
机制编译期代码生成运行时反射 + 容器运行时反射容器（fx 的内核）直接写 NewX(NewY(...))泛型 + 运行时容器
接线时机wire genfx.New 启动时dig.New + Invoke编译期（就是代码）运行期 do.Invoke
可读性最高，生成的就是手写代码中，图在运行时低，注入靠 tag最高，但随规模线性膨胀中
生命周期钩子无，cleanup 手工串完整：OnStart/OnStop、信号、超时无自己写有 scope/health 钩子
模块化ProviderSet 组合fx.Module + Provide/InvokeProvide 选项包拆分do.Package
类型冲突 / 失败暴露生成期报错，构建期暴露运行期报错，启动期 panic运行期报错（可用 name 区分）编译器不管运行期报错
适合中大型服务、要可读装配长生命周期守护进程、要钩子库内部动态装配小项目、依赖 < 10 个想要泛型 API 的容器

一句话决策：装配要「看得见、断得住、错在编译期」选 wire；要进程生命周期管理（OnStart/OnStop、信号、优雅退出编排）选 fx；只想在库里做动态解析用 dig；依赖不到十个就手写。

什么时候不该用 wire：小项目或 CLI——手写三行构造函数比维护 tag + 生成文件直观；团队不接受「生成代码入库」，review 时没人看 wire_gen.go；依赖图需要运行时动态变化（插件、按请求构造），wire 是静态图；需要开箱即用的生命周期与健康检查，wire 只给一个 cleanup；以及在意上游活跃度——项目已归档，长期只能靠 fork 维护。
