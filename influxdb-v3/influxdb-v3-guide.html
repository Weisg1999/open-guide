Rust 重写 · FDAP 架构 · SQL 查询 · 对象存储优先 —— InfluxData 历时四年从零重写的新世代时序平台：近乎无限的基数支持、开放列式格式与标准 SQL 查询。

1. 项目简介入门

InfluxDB 3 是 InfluxData 历时四年多、用 Rust 从零重写的时序数据库（仓库 github.com/influxdata/influxdb，2025.4 GA）。它没有延续 v2 的「TSM 引擎 + Flux 语言 + TSI 索引」自研路线，而是整体迁移到 Apache 开放分析生态——动机来自用户呼声最高的三个能力：

1.1 三大动机

♾️无限基数

v2 的 TSI 索引在高基数下内存爆炸；v3 列式架构让 tag 组合数不再是性能枷锁。

🪣历史数据放对象存储

冷数据沉到 S3 等廉价存储，同时保持可查询——成本与查询能力兼得。

📜标准 SQL

弃用自研 Flux，查询语言回归工业标准，BI / 分析工具直接对接。

1.2 两条产品线（同一内核）

版本定位关键差异
Core（开源）高速「近期数据引擎」单进程；内存中保留近期数据 + last cache；历史查询受 Parquet 文件数限制（默认 432 个文件 ≈ 72 小时 @ 默认 10 分钟文件粒度）；MIT / Apache-2 许可
Enterprise（商业）完整平台Compactor 后台压缩、长期历史查询、HA、多节点、增强安全

典型场景：DevOps / IoT 监控AI Agent 可观测高频传感数据需要 SQL 直接分析时序

2. 核心架构：FDAP 栈中级

v2 是「自研一切」（TSM 引擎 + Flux 语言），v3 是「站在开源分析生态上」：SQL、Flight SQL、与 pandas / Polars / DuckDB 的互操作几乎免费获得。四个 Apache 项目的首字母，自上而下拼成 FDAP：

2.1 写入路径（diskless 架构）

  • 近期数据在 WAL 与内存 buffer 中，查询「最近几分钟」不碰对象存储——低延迟；
  • 每 10 分钟把内存数据整块转成 Parquet（gen1 文件）写入对象存储；Catalog 记录「哪段时间在哪个文件」；
  • Enterprise 的 Compactor 把小 gen1 文件合并成更大的 gen2 / gen3 层——历史查询性能与成本的关键（Core 没有后台 Compactor，所以查询触碰的文件数受限）；
  • diskless：持久状态可全部放对象存储，进程本身无状态化。
💡 K8s 友好：diskless 架构下进程挂了重启即恢复——持久状态全在对象存储（+ 本地 WAL），天然适合容器编排。

2.2 查询路径

  • SQL 完整语法：JOIN、窗口函数、CTE——v2 Flux 里费劲的 join 现在是一句 SQL；
  • 兼容 InfluxQL（v1 语法子集）帮助迁移；
  • 多个查询引擎可经 Arrow Flight 直连 InfluxDB 3 的 Parquet 生态——DuckDB 查 S3 上的 InfluxDB Parquet 是官方演示场景。
-- 窗口聚合：v2 Flux 里费劲的 join / 分窗，v3 是一句 SQL
SELECT host,
       DATE_BIN(INTERVAL '5 minutes', time, TIMESTAMP '1970-01-01T00:00:00Z') AS window,
       AVG(usage_idle) AS idle
FROM cpu
WHERE time > NOW() - INTERVAL '1 hour'
GROUP BY host, window
ORDER BY window;
⚠️ Flux 不支持：v3 无法运行 Flux 查询，官方迁移工具负责转换常见查询——存量 Flux 资产要提前评估（见第 5、6 节）。

2.3 数据模型：与 v2 的对照

Line Protocol 仍是写入协议：cpu,host=node1 usage_idle=91.2 1735689600000000000，各片段落到 v3 的形态：

2.4 Processing Engine：嵌入式 Python VM

v3 内嵌 Python 虚拟机，插件在数据写入路径上对 Arrow 批零拷贝执行——这是 v2 Tasks 的官方继任者：

  • 触发器：WAL flush 事件 / 定时（cron）；
  • 用途：降采样（替代 v2 Task）、异常检测、告警转发（webhook / PagerDuty）、数据清洗；
  • 插件就是 Python 文件（官方标准插件库 + 自定义）。
# 处理引擎插件形态示意：对写入路径上的 Arrow 批直接处理
def process_batch(batch, context):
    if batch["cpu"].mean() > 90:
        context.alert("cpu high")

3. 使用实战（Go）初级

以下示例基于官方 Go 客户端 influxdb3-go/v2；HTTP API 部分任何语言都能零依赖接入。

3.1 写入与查询（influxdb3-go）

client, err := influxdb3.New(influxdb3.ClientConfig{
    Host:       "http://localhost:8181",
    Token:      "my-token",
    Database:   "metrics",
})
defer client.Close()

// 写入 Line Protocol
points := []string{
    "cpu,host=node1,region=cn usage_idle=91.2,usage_user=6.1",
    "cpu,host=node2,region=cn usage_idle=88.7,usage_user=7.9",
}
err = client.Write(context.Background(), points)

// SQL 查询：DATE_BIN 按 5 分钟分窗聚合
query := `SELECT host, DATE_BIN(INTERVAL '5 minutes', time, TIMESTAMP '1970-01-01T00:00:00Z')
                 AS window, AVG(usage_idle) AS idle
          FROM cpu WHERE time > NOW() - INTERVAL '1 hour'
          GROUP BY host, window ORDER BY window`
it, err := client.Query(context.Background(), query)
for it.Next() {
    row := it.Value()
    fmt.Println(row["host"], row["window"], row["idle"])
}

3.2 HTTP API（任何语言零依赖接入）

# 写入（Line Protocol）
curl -X POST "http://localhost:8181/api/v3/write_lp?db=metrics&precision=nanosecond" \
  -H "Authorization: Bearer $TOKEN" \
  --data-binary 'cpu,host=node1 usage_idle=91.2'

# SQL 查询（可返回 JSON / Arrow / CSV / Parquet 格式）
curl -X POST "http://localhost:8181/api/v3/query_sql" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"db":"metrics","q":"SELECT host, AVG(usage_idle) FROM cpu WHERE time > NOW() - INTERVAL 1 HOUR GROUP BY host"}'

3.3 管理命令

# 建库 / 令牌 / 查询
influxdb3 create database iot --retention-period 30d
influxdb3 create token --all-databases
influxdb3 query "SELECT * FROM cpu LIMIT 5" --database metrics

# 启用处理引擎插件（WAL flush / cron 定时触发）
influxdb3 enable --plugin downsample.py --trigger tables --database metrics
influxdb3 plugin list

4. Core vs Enterprise：选型必读中级

同一内核、两条产品线，最大的分界在历史查询与集群能力：

能力Core（开源）Enterprise
近期数据查询（WAL / 内存 / last cache）✅ 低延迟✅
历史查询范围受 --query-file-limit 限制（默认 432 个 Parquet 文件 ≈ 3 天 @10min 粒度，可调大但吃内存）✅ Compactor 合并 + 完整历史
高可用 / 多节点❌ 单进程✅
后台 Compaction❌✅
安全增强（审计等）基础✅

4.1 「72 小时」限制的本质

💡 别被「72 小时」误导：Core 的限制本质是单次查询可触碰的 Parquet 文件数（432），不是时间硬编码——432 × 10 分钟 ≈ 72 小时只是默认文件粒度下的换算。写入持续、查询范围小的时候，Core 存得远不止 72 小时的数据，只是查询受限。需要「长期廉价保留 + 全量历史查询」→ Enterprise，或自行把 Parquet 交给 DuckDB / Spark 生态。

5. 版本演进速览了解

  • 2020–2024IOx 项目：验证 Arrow / Parquet 列式路线（v3 的技术前身）
  • 2025.1 → 2025.3Alpha → Beta：Rust 重写内核逐步开放试用
  • 2025.4GA：Core（开源）与 Enterprise 同时正式发布
  • 2025 全年内核快速迭代：last cache 优化、InfluxQL 兼容扩展、Processing Engine 插件生态丰富
  • 2026Enterprise 新一代存储引擎：.pt 文件格式、column families、Gorilla / delta-delta 压缩回归时序特化路线，--upgrade-pacha-tree 平滑迁移——解决 Parquet 通用格式在单序列高频查询上的短板
  • 3.xFlux 正式终止：v2→v3 迁移以 bucket→database 重写为主（官方迁移工具覆盖常见 Flux 查询）

6. 常见坑与最佳实践中级

1Core 别当长期库用

Core 定位是「最近数据引擎」，把 90 天查询需求压给 Core 必然撞文件数限制——要么 Enterprise，要么把 Parquet 出湖给 DuckDB / Spark 等分析引擎。

2tag / field 选型习惯保留

过滤列（tag）仍决定谓词下推效率；高基数不再是禁区，但会放大存储成本。

3写入仍走 Line Protocol 批量化

单点 HTTP 写入的性能浪费与 v2 时代相同——攒批再写。

4时间谓词必须带

无 time 过滤的查询会扫全部文件——SQL 方言没变，代价还在。

5对象存储选型

S3 / R2 / MinIO 均可（file 模式仅适合试验）；MinIO 是自托管常见组合。

6内存管理

write buffer 与 last cache 常驻内存，容量规划按「写入速率 × gen1 周期」估算。

7吃足 Arrow 生态红利

分析场景直接用 DuckDB 查 Parquet、Python 走 Flight SQL 拿 Arrow 批——比 REST JSON 快一个量级。

8迁移策略

双写并行（v2 + v3）观察查询等价性；Flux 查询先用官方转换工具过一遍再人工修。

9版本跟进

3.x 迭代快，升级前读 changelog（Core 的配置项偶有更名）。

7. 选型小结决策

场景建议
新监控 / 可观测项目、想用 SQLInfluxDB 3 Core 起步
高基数（成千上万维度组合）事件数据v3（v2 请直接跳过）
长保留 + 全量历史 + HAInfluxDB 3 Enterprise；或 Core + Parquet 外部分析
已有大量 Flux 资产先评估迁移成本；v2.7 维护期内规划
纯指标采集 + PromQLPrometheus / VictoriaMetrics 更对口（v3 不是 PromQL 替代品）
