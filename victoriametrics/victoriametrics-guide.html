Prometheus 长期存储与全局查询的两条路线：二者解决的是同一个问题——本地 TSDB 保留期有限、单机不可扩展、多集群没有统一视图；但架构完全不同，VictoriaMetrics 是自研一体化时序库直接承接写入与查询，Thanos 是把 Prometheus 原生 TSDB block 搬进对象存储再叠一层联邦查询层。 上游：https://github.com/VictoriaMetrics/VictoriaMetrics · https://github.com/thanos-io/thanos　|　主线：VictoriaMetrics v1.156.0（1.x，2026-11-09）/ Thanos v0.42.5（0.42.x，2026-10-27），整理于 2026-11　|　协议：社区版均为 Apache-2.0（VictoriaMetrics 企业版功能另需商业许可；Thanos 为 CNCF Incubating 项目）

1. 项目简介入门

Prometheus 篇讲清了「怎么拉、怎么存、怎么查、怎么告」，但它的本地 TSDB 有三条硬边界，正是二者存在的理由：保留期有限（默认 --storage.tsdb.retention.time=15d，只落本地盘，无廉价归档）；单机无副本无分片（重启期间不可查、盘坏即丢，HA 靠跑两个实例各拉一份但查询时数据重复）；联邦不等于长期存储（上层只拉下层算好的瞬时值，不做历史归档、跨集群去重与全局 PromQL）。

共同问题VictoriaMetrics 的答案Thanos 的答案
存得久、存得省自研 TSDB + 高压缩比，本地盘即可，一个二进制起全套block 上传对象存储（S3/MinIO/COS），近乎无限保留
多集群统一查询数据进同一套 vmselect，天然全局Query 通过 Store API 联邦 Sidecar 与 Store Gateway
HA 去重写入侧打标签、查询侧 dedup--query.replica-label 在查询时合并副本
接入方式remote write 接收为主，也能自己抓（vmagent）外挂 Sidecar（pull 不动采集链路）或 Receive（push 收 remote write）

定位差异一句话：VictoriaMetrics 是「换一个更强的存储与查询引擎」，可替掉 Prometheus 的远端；Thanos 是「给已有 Prometheus 加一层」，采集链路原封不动。前者求极简运维与资源效率，后者求零侵入与无限容量。

  • 适用：跨集群/跨地域统一视图、年级容量与 SLO 趋势、HA 去重、降低单机资源占用、多租户隔离
  • 不适合：单集群且保留期几周内（直接调大 retention.time）、日志与单条请求上下文（用 Loki 篇）、SQL 明细分析（用 ClickHouse 篇）、业务时序与精确计费（用 InfluxDB v3 篇）

对象存储是 Thanos 的地基，自建参照 MinIO 篇：bucket 容量、请求次数、跨区流量直接决定账单与查询延迟，这在 VictoriaMetrics 路线上是不存在的成本项。

3. 核心概念与原理核心

3.1 共同起点：Prometheus TSDB block

Thanos 搬运的就是 Prometheus 每 2 小时从内存 Head 落盘的不可变 block：

<ULID>/
├── chunks/      # 压缩样本（XOR + 时间戳 delta-of-delta）
├── index        # 倒排索引：label=value -> series ID
├── meta.json    # ULID、[minTime,maxTime]、compaction 层级
└── tombstones   # 删除标记

block 自包含、不可变，天然适合整体上传与缓存——Thanos 全靠这一点；VictoriaMetrics 完全不复用 block，而把样本按自己的结构重排，故压缩率、查询路径、扩容方式从根上不同。

3.2 VictoriaMetrics：一体化存储与集群数据流

单节点把采集、存储、查询、UI（vmui）塞进一个二进制，靠 flag 配置；集群版拆成三类节点：

 scrape / remote write ─► vmagent（抓取、relabel、WAL 队列）
                            │ remote write
                            ▼
 写入 ─► vminsert（无状态，按 accountID 一致性哈希选 vmstorage）
                            │
      ┌─────────────────────┼─────────────────────┐
      ▼                     ▼                     ▼
 vmstorage(shard)     vmstorage(shard)     vmstorage(shard) ← 唯一有状态、保存数据
      └─────────────────────┼─────────────────────┘
                            ▼
 查询 ─► vmselect（无状态，扇出、合并、去重）──► Grafana / vmalert
  • vmstorage 有状态且不可随意替换，扩容要改 -storageNode 并做数据再平衡；vminsert/vmselect/vmagent 无状态，可随意水平扩。
  • 多租户靠 URL 前缀：/insert/42/prometheus/api/v1/write 与 /select/42/prometheus/api/v1/query 中的 42 即 accountID；集群只认数字 ID，名称、鉴权、配额要放前置网关（vmauth）。
  • vmalert 单独评估 recording/alerting rules 并回写结果、发 Alertmanager，相当于 Prometheus 的 rule evaluator + Thanos Ruler。

3.3 VictoriaMetrics：压缩、MetricsQL 与内存/磁盘取舍

高压缩比来自按 metricName 聚簇存储使重复标签字典化、时间戳与值分别 delta/XOR 变长编码、索引与数据按时间分区。代价是用内存换磁盘：活跃 series 索引、TSID 缓存、merge 缓冲区常驻内存，内存不足不会优雅降级而是 OOM。

  • 容量规划要按 active series 数估内存，而非磁盘容量；-retentionPeriod=12months 是全局滚动删除，按整月分区、非精确到秒，社区版只有单一保留期（多级保留/自动降采样是企业版能力）。
  • MetricsQL 是 PromQL 超集：WITH 模板、rollup_* 系列、label_match/label_mismatch、*_over_time 扩展。关键行为差异：increase()/rate() 不做外推，同一 counter 在 VM 与 Prometheus/Thanos 上可能差几个百分点——迁移 SLO 阈值必须重新校准。
# MetricsQL 专属：WITH 模板函数抽取公共聚合
WITH (common = {job="app", env="prod"}, rps(m) = sum(rate(m[5m])) by (cluster))
rps(app_http_requests_total{common})
# rollup_* 系列：在整个 lookbehind 窗口上聚合而非逐点计算
rollup_rate(app_http_requests_total[5m])
# 纯 PromQL 子集：两条路线都能跑，Grafana 面板直接复用
sum by (cluster) (rate(app_http_requests_total[5m]))

3.4 Thanos：block 上传与 Store API 联邦查询

Thanos 不改采集，外挂一组组件，组件间用 gRPC Store API 通信：

 Prometheus ──(本地 TSDB)──► Sidecar ──上传 block──► 对象存储 bucket
      │ Sidecar 同时把「近 2h 热数据」通过 StoreAPI 暴露（否则刚产生的数据查不到）
      │                                  │ 读历史 block
      │                                  ▼
      │                        Store Gateway（索引缓存 + 惰性加载 chunks）
      │                                  │ Store API (gRPC)
      └──────────► Query / Query Frontend（扇出全部后端、合并、去重）──► Grafana
  • Query Frontend 在 Query 前做查询拆分、步骤对齐与结果缓存，是长区间查询必配；Grafana 只当它是一个 Prometheus 数据源。
  • push 形态：用 Receive 替代 Sidecar，直接收 remote write、本地攒成 block 再上传，适合不想每集群跑 Prometheus 或跨网络边界；代价是丢了拉取模型自带的 up 健康探测，且要自己设计 hash 环与副本。

3.5 Thanos：downsampling、副本去重与 Compactor

Compactor 串行处理单个 bucket：压缩小 block、应用保留策略、生成降采样数据。

 raw block（原始精度）──保留 --retention.resolution-raw
      ├─► 5m 降采样 ──保留 resolution-5m
      └─► 1h 降采样 ──保留 resolution-1h
 查 90 天曲线自动选 1h 数据：扫描样本降到 1/120，这是「长区间不炸」的根因

降采样保留 count/sum/min/max，rate、histogram_quantile 仍可算但精度下降，不能替代原始数据。副本去重：HA 两份数据标签只差 prometheus_replica，Query 用 --query.replica-label=prometheus_replica 声明「该标签不参与 series 身份」，合并时折叠成一条；漏配则所有曲线数值翻倍、告警误报，配合 external_labels（cluster/region）标全局唯一来源才不会误伤不同集群。

3.6 两种架构的本质分野

VictoriaMetricsThanos
查询放大扇出到 N 个 vmstorage，无对象存储往返，延迟稳定扇出到 N 个 Sidecar + M 个 Store Gateway，长区间天然放大，靠 downsampling + Query Frontend 压制
成本结构本地盘 + 内存，数据不出口，成本可预测容量便宜，但 PUT/GET 请求费、跨区流量、索引缓存是隐性成本
运维复杂度单节点零运维；集群版 3 类节点5~7 类组件 + bucket 生命周期 + Compactor 单例约束
与 Prometheus 关系可替换/承接，采集可用 vmagent 重写严格外挂，复用原生 TSDB 与规则语义
PromQL 兼容性MetricsQL 超集，行为细节有差异原生 PromQL 语义，迁移成本最低

与 Grafana Mimir / Cortex 的边界：二者同属「remote write + 对象存储」家族，Mimir 主打原生多租户（AGPLv3，嵌入商业产品需法务评估），Cortex 是其上游前身（Apache-2.0，CNCF Incubating）。Thanos 与它们的根本区别是是否保留每集群独立 Prometheus + block 上传路径；VictoriaMetrics 根本区别是不依赖对象存储。Prometheus + 联邦只是层级聚合，三者都不提供长期归档与全局去重，不在同一能力档位。

3.7 MetricsQL：PromQL 超集，多出来的那部分

MetricsQL 的目标是「PromQL 能跑的都能跑，跑不顺的给你更好的写法」。它兼容 PromQL 的语法与函数名，但在几个地方做了实质增强：

能力PromQLMetricsQL用处
空结果兜底需要 or vector(0)expr default 0大盘上的「无数据」变成 0，不用拼伪序列
按标签过滤另一查询无直接语法q1 if q2 / q1 ifnot q2用另一条查询的结果裁剪标签集，替代 and on() 的绕法
合并多查询or 要求标签完全一致union(q1, q2, ...)同名指标来自不同 job 时合并
保留指标名rate() 后名字丢失，需 label_replacerate(...) keep_metric_names告警模板里直接用 {{ $labels.__name__ }}
分页无limit_offset(offset, limit, expr)大基数标签枚举
尖刺观测只能取瞬时或区间聚合rollup_rate() / rollup_delta() 返回 min/max/avg看「这一分钟有没有尖刺」，而不是只看均值
标签改写label_replace / label_joinalias / label_set / label_del / label_copy批量改写，语法更直观
直方图histogram_quantile同函数 + histogram_avg / histogram_stddev / buckets_limit原生 histogram 的补充统计

几个高频写法：

# 大盘上「没有请求」显示 0，而不是 No data
sum(rate(http_requests_total[5m])) by (route) default 0

# 只看生产环境：用另一条查询裁剪标签
sum(rate(http_requests_total[5m])) by (route) if on (instance) up{env="prod"} == 1

# 保留指标名，告警里直接用名字
rate(node_cpu_seconds_total{mode="idle"}[5m]) keep_metric_names

# 看 5 分钟内的尖刺，而不只是均值
rollup_rate(http_request_duration_seconds_bucket[5m])

# 分页枚举高基数标签
limit_offset(0, 100, count by (user_id) (requests_total))

需要留意的语义差异：

  • rate() / increase() 的外推策略不同。Prometheus 按区间边界外推，VM 会在 counter reset 与数据缺口上做更保守的处理。同一段数据在两侧算出的值可能差几个百分点，迁移时不要拿旧值当基线做同比。
  • @ 修饰符与子查询都支持，但 @ start() / @ end() 在 VM 的查询参数下语义以请求区间为准，Grafana 里改时间范围会连带改变结果。
  • 多租户查询要带 extra_label 或走 /select/{accountID}/prometheus/api/v1/query。单机版没有租户概念，集群版忘了带租户 ID 会查不到数据，而不是报错。
  • histogram_quantile 对原生 histogram 的支持是 VM 的扩展；如果指标来自 Prometheus 的经典 bucket，行为与 PromQL 一致。

迁移 Grafana 大盘时，绝大多数 PromQL 可以直接用；真正要改的是那些依赖「空结果就是空」的面板——VM 的 default 会让它们从 No data 变成 0，视觉上反而更清楚，但告警阈值要重新确认。

4.3 采集端：Prometheus 配置与 Go 应用埋点

# prometheus.yml —— external_labels 必须全局唯一，否则 Thanos 分不清来源
global:
  scrape_interval: 15s
  external_labels: { cluster: cn-shanghai-a, prometheus_replica: replica-0 }
scrape_configs:
  - job_name: "app"
    static_configs:
      - targets: ["localhost:8080"]
remote_write:
  - url: http://vmsingle:8428/api/v1/write   # 路线 A：推给 vmsingle / vminsert
    queue_config: { max_samples_per_send: 10000, capacity: 20000 }
  # - url: http://localhost:10908/api/v1/receive  # 路线 B：推给 Thanos Receive（见 4.5）
package main

import (
    "log"
    "net/http"

    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/collectors"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

func main() {
    reg := prometheus.NewRegistry()
    reg.MustRegister(collectors.NewGoCollector(),
        collectors.NewProcessCollector(collectors.ProcessCollectorOpts{}))
    requests := prometheus.NewCounterVec(prometheus.CounterOpts{
        Name: "app_http_requests_total",
        Help: "Total HTTP requests handled, labelled by route and status.",
    }, []string{"route", "code"})
    reg.MustRegister(requests)
    mux := http.NewServeMux()
    mux.HandleFunc("/api/users", func(w http.ResponseWriter, r *http.Request) {
        requests.WithLabelValues("/api/users", "200").Inc() // 用路由模板，勿用 r.URL.Path
        w.WriteHeader(http.StatusOK)
        _, _ = w.Write([]byte("ok"))
    })
    mux.Handle("/metrics", promhttp.HandlerFor(reg, promhttp.HandlerOpts{}))
    log.Println("listening on :8080, metrics at /metrics")
    log.Fatal(http.ListenAndServe(":8080", mux))
}

用独立 Registry 而非默认注册表避免重复注册 panic；标签只放有界枚举，见 Prometheus 篇。批处理补数可走 VM 的 /api/v1/import/prometheus 文本导入端点，无需 protobuf/snappy。

4.4 Go：一套代码查询两条路线的全局视图

package main

import (
    "fmt"
    "io"
    "log"
    "net/http"
    "net/url"
)

// vmsingle / vmselect / Thanos Query 都兼容 Prometheus /api/v1/query，
// 因此同一段代码可无缝切换后端，拿到跨集群的全局结果。
func query(endpoint, expr string) (string, error) {
    u := endpoint + "/api/v1/query?query=" + url.QueryEscape(expr)
    resp, err := http.Get(u)
    if err != nil {
        return "", err
    }
    defer resp.Body.Close()
    b, err := io.ReadAll(resp.Body)
    return fmt.Sprintf("%s %s", resp.Status, b), err
}

func main() {
    expr := `sum by (cluster) (rate(app_http_requests_total[5m]))`
    for _, ep := range []string{"http://localhost:8428", "http://localhost:10902"} {
        out, err := query(ep, expr)
        if err != nil {
            log.Fatal(err)
        }
        fmt.Println(ep, out)
    }
}

4.6 集群扩缩容与容量规划

集群版的三类节点，扩容语义完全不同，不能一起加机器：

节点是否有状态扩容效果注意
vminsert无状态提升写入吞吐，线性前面挂负载均衡；-replicationFactor 决定副本数
vmselect无状态（有缓存）提升查询并发，近似线性缓存命中率随实例增多下降，必要时收敛副本数
vmstorage有状态提升容量与查询并行度扩容后旧数据不迁移，新数据按一致性哈希落到新节点；查询会扇出到全部 storage

两个和「多副本」直接相关的参数：

# 写入 2 副本：同一份样本进两个 vmstorage，单节点故障不丢数据
-replicationFactor=2

# 多副本/多次抓取的去重窗口：同一 series 在窗口内的重复样本只留一份
-dedup.minScrapeInterval=30s

-dedup.minScrapeInterval 的取值要和采集间隔对齐。设成 30s 而实际 15s 抓一次，会丢掉一半样本；设成 0（关闭）而两个 vmagent 都在抓，查询会看到双倍数值。

容量估算（数量级判断，最终以压测为准）：

磁盘 ≈ 活跃 series × (1 / 采集间隔) × 字节/样本 × 保留秒数
内存 ≈ 活跃 series × 1~2 KB（索引 + 倒排 + 缓存，随标签基数上升）

例：50 万 series，15s 间隔，保留 90 天，按 0.8 B/样本
   samples/s = 500000 / 15 ≈ 33,333
   磁盘 ≈ 33333 × 86400 × 90 × 0.8 ≈ 207 GB（未计副本与 WAL 余量，实际留 1.5 倍）

比公式更可靠的是直接读 VM 自己的指标：

指标含义用途
vm_rows_inserted_total每秒写入行数对照磁盘增长，验证估算
vm_slow_queries_total慢查询计数调 -search.maxQueryDuration 或优化 PromQL
vm_cache_size_bytes各类缓存占用判断内存是否被缓存吃满
vm_active_merges / vm_rows_merged_total后台合并压力合并跟不上会导致查询变慢
vm_free_disk_space_bytes剩余磁盘保留期到顶前的预警

调参优先级：先限 -memory.allowedPercent（默认 60），避免缓存把机器吃满触发 OOM；再限 -search.maxQueryDuration（默认 30s），防止一个大盘拖垮查询；最后才考虑加 vmselect。

4.7 迁移：从 Prometheus / Thanos 到 VM

按起点分三条路，切换方式不同，但原则一样：先双写观察，再切读，最后下线旧组件。

路径 A：单机 Prometheus，想换成 VM

# 1) 起 VM，保留期与单机一致或更长
./victoria-metrics-prod -storageDataPath=/data/vm -retentionPeriod=12

# 2) Prometheus 加 remote_write，双写一段时间
# prometheus.yml
remote_write:
  - url: http://vm.internal:8428/api/v1/write
    queue_config:
      max_samples_per_send: 10000

# 3) 用 vmagent 接管采集（替代 Prometheus 的 scrape）
# vmagent 支持磁盘缓冲，网络抖动不丢样本
./vmagent-prod -promscrape.config=/etc/prometheus/prometheus.yml \
  -remoteWrite.url=http://vm.internal:8428/api/v1/write \
  -remoteWrite.tmpDataPath=/data/vmagent-buf

# 4) 历史数据：先把 Prometheus 快照导出，再导入 VM
curl -X POST http://prom.internal:9090/api/v1/admin/tsdb/snapshot
./vmctl prometheus --prom-snapshot=/var/lib/prometheus/snapshots/<id> \
  --vm-addr=http://vm.internal:8428

路径 B：Prometheus + Thanos，想收敛成 VM

Thanos 的价值是「对象存储 + 全局查询」，VM 的价值是「本地盘 + 低查询放大」。切换时不要试图把 bucket 里的 block 全量导入——几年数据导入耗时远超收益，通常只迁最近 30–90 天，更早的留在 bucket 里只读归档。步骤：vmagent 双写 → 新数据进 VM → Grafana 数据源切到 VM → 旧 Thanos 保留只读 → 保留期到后下线。

路径 C：Mimir / Cortex，想降成本

这两者与 VM 同属「remote write 接收」，切换最平滑：把 remote_write 的 URL 指到 vminsert，观察写入与查询，确认无缺样本后切读。注意 Mimir 的 X-Scope-OrgID 与 VM 的租户路径（/insert/{accountID}/...）不是一回事，网关层要做头转换。

规则也要跟着迁：Prometheus 的 rule_files 拆成 vmalert 的 -rule 目录（兼容 Prometheus rule YAML），alerting 段指向 Alertmanager 或夜莺。Recording rules 里对 rate() 的依赖要在 VM 上重算基线，原因见 3.7 的外推差异。

4.8 备份、快照与容灾

单机版没有「备份命令」，只有快照：

# 创建硬链接快照（几乎瞬时，不占额外空间）
curl -X POST 'http://vm.internal:8428/snapshot/create'
# 返回 {"status":"ok","snapshot":"20261118T091500Z-xxxx"}

# 备份快照目录（rsync / 对象存储同步均可）
rsync -a /data/vm/snapshots/20261118T091500Z-xxxx/ backup:/vm-snapshots/

# 用完删除，否则快照会阻止旧数据被回收
curl 'http://vm.internal:8428/snapshot/delete?snapshot=20261118T091500Z-xxxx'

集群版用 vmbackup 直接对接对象存储，靠 vmstorage 的 snapshot API 做一致性点：

vmbackup -storageDataPath=/vmstorage-data \
  -snapshot.createURL=http://vmstorage-0:8482/snapshot/create \
  -dst=s3://my-bucket/vm-backup/$(date +%Y%m%d)

容灾拓扑按 RTO 选：

方案RTO成本适用
单机 + 每日快照小时级低内部监控、可容忍丢一天
-replicationFactor=2 跨 AZ分钟级（单节点故障无感）中（存储翻倍）生产默认
双集群 + vmagent 双写秒级切换高核心 SLO、跨region
对象存储归档 + vmrestore小时级低合规留存、冷备

最后一条经验：备份要演练恢复。vmrestore 到一台新机器、起 vmselect 查一个月前的数据，比备份成功率报表更有说服力。

实战要点：先算保留期与基数：本地盘能撑住就别急着上集群；需要跨集群全局视图时，Thanos 的 Query 层更自然，单集群高写入则优先 VM。

6. 常见坑与最佳实践避坑

  1. 单机够用却硬上分布式：单集群、周级保留直接调大 --storage.tsdb.retention.time 最省事。对策：先确认真的需要全局视图/年计保留再引入。
  2. -retentionPeriod 单位写错：写成 12 或 12d 语义都不对。对策：用 12months/2y 带单位写法，并知道删除按整月分区、非精确到秒。
  3. Thanos 漏配唯一 external_labels：两个集群都叫 cluster=prod 会被当成同一来源。对策：每个 Prometheus 写全局 external_labels，上线前 thanos tools bucket inspect 核对。
  4. HA 双副本数据翻倍：漏了 --query.replica-label，rate() 直接翻倍、告警全误报。对策：所有副本用同一 replica 标签名，Query 与 Ruler 都声明，用 count(up) by (cluster) 验证。
  5. 长区间查询直接打 Query：一年曲线把请求放大到全部 block，拖垮 Store Gateway。对策：必配 Compactor 降采样 + Query Frontend，面板限制最大时间范围，raw 只用于短窗口排障。
  6. 只算容量不算请求费与流量：Store Gateway 反复拉索引/chunks 产生大量 GET。对策：留足本地缓存盘、监控 bucket 操作数与跨区流量、同地域部署（见 MinIO 篇）。
  7. 把 VM 当成「省内存」方案：高压缩比是用内存换磁盘，索引与缓存常驻内存。对策：按活跃 series 数估内存，监控 vm_* 自监控指标，OOM 前先扩内存或减基数。
  8. 高基数标签照搬：user_id/trace_id/原始 URL 做标签，两条路线都会爆。对策：标签只放有界枚举，明细进日志/链路（OpenTelemetry 篇），查询侧用 -search.maxSeries 限流兜底。
  9. 单节点与集群端点混用：集群版必须带 /insert/<accountID>/... 前缀，直接 POST /api/v1/write 会 404。对策：配置时明确区分 vmsingle 与 vminsert/vmselect 路径，accountID 由网关注入。
  10. 多租户只靠路径、无鉴权：集群只认数字 accountID 不校验身份。对策：前置 vmauth/API 网关做认证、配额与租户映射，别把 vmselect 直接暴露给租户。
  11. 把 MetricsQL 搬到 Thanos/Grafana：WITH、rollup_*、label_match 在标准 PromQL 直接语法错。对策：公共面板坚持用 PromQL 子集，VM 专属扩展只放 VM 数据源并注明不可移植。
  12. increase/rate 跨路线对不上：MetricsQL 不外推，同一 counter 差几个百分点。对策：迁移 SLO 阈值重新校准，别把告警表达式在两条路线间原样复制。
  13. remote write 无队列、抖动丢数据：不落盘即内存排队。对策：开启 WAL/持久化队列（-remoteWrite.tmpDataPath、queue_config），监控 prometheus_remote_storage_* 失败与积压。
  14. Compactor 多实例抢同一 bucket：会损坏 block；Sidecar 跨集群写同一 bucket 也会重叠。对策：每 bucket 只跑一个 Compactor，用 relabel 或独立 bucket 隔离租户，定期 bucket verify。
  15. 拿它存日志/明细/精确计费：时序库为聚合监控设计。对策：日志走 Loki 篇、明细走 ClickHouse 篇、业务时序走 InfluxDB v3 篇。
  16. 不看自监控：查询变慢、block 上传滞后、去重失效都不会主动报错。对策：给各组件配抓取与告警（compactor 进度、store 延迟、bucket 错误率、query 并发），共用 Alertmanager。

生产警示：remote write 的队列与超时配置不当会拖垮 Prometheus 本身；Thanos 的 downsampling 会让原始精度丢失，排障必须保留 raw block 的查询入口。

按决策维度落点：

决策维度倾向理由
单机够用（单集群、周级保留）都别上，调大 retention.time引入分布式系统是无谓成本

超长区间（年级）历史查询Thanos唯一原生降采样，长区间扫描成本最低

一句话决策结论：想用最少组件、最低资源把 Prometheus 的存储和全局查询一次做好 → VictoriaMetrics；已重度依赖 Prometheus + 对象存储、要保持采集链路与 PromQL 语义原封不动 → Thanos。二者不是「谁更好」，而是「换引擎」与「加一层」两条方向相反的路。

何时不该用：

  • 单机就能满足（单集群、保留期 < 2 个月、无跨集群查询）：直接调大 Prometheus 本地保留期，别引入任何一套。
  • 只有对象存储、却没有跨集群/长期需求：Thanos 的组件与 bucket 治理成本收不回来。
  • 要 SQL 分析、明细事件、日志检索或精确计费：四条路线都是聚合型时序监控，明细分别走 ClickHouse、Loki、InfluxDB v3。
  • 对 AGPLv3 敏感且要把监控系统嵌入对外产品：避开 Mimir，回到 Apache-2.0 的 VM / Thanos / Cortex 并让法务确认。
  • 没有对象存储运维能力、也不想自建（MinIO 篇）：优先 VM 单节点或托管云监控，别硬扛 bucket 生命周期。

落地顺序：先统一 cluster/replica 标签规范与 OpenTelemetry Resource → 打通 remote write → 配好去重与降采样 → 再上全局面板与告警。先看标签与保留期，再选引擎，绝大多数「查询慢/数据翻倍/账单爆炸」都是这两件事没定好。
